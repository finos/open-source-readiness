# InnerSource Blueprint

A common blocker to InnerSource adoption is the gap between understanding the concept and knowing how to implement it. While teams may support the idea of open collaboration, many struggle to answer practical questions such as:
- What does an InnerSource-ready project look like?
- What documentation is required?
- How should external contributions be managed?
- Who is responsible for governance and decision-making?
- How can contributors discover and engage with the project?

Without clear guidance, teams are often left to define their own approaches. This can lead to inconsistent practices, increased onboarding effort, and a fragmented contributor experience—ultimately slowing adoption.

The InnerSource Blueprint is a practical solution to this adoption challenge.

Rather than expecting every team to design its own InnerSource model, the blueprint provides a predefined path that helps teams establish projects in a way that is consistent, discoverable, and easy to contribute to.

## Minimum Requirements for an InnerSource Project
To reduce barriers to contribution and create a consistent experience across projects, every InnerSource project should meet a minimum set of requirements before it is promoted to the wider engineering community.

At a minimum, a project should provide the foundational documentation recommended by the InnerSource Commons patterns. These documents ensure that potential users and contributors can quickly understand the project, learn how to engage with it, and identify where to seek support.

An InnerSource project should clearly communicate:
- **Project Purpose:** Contributors need to understand what the project does, who it is intended for, and why it exists. This information is typically captured in a README
- **Contribution Process:** Contributors need clear guidance on how they can participate in the project. This information is typically captured in a CONTRIBUTING guide
- **Communication and Support:** Potential contributors should know who maintains the project and how to engage with the community. Communication information may be included within the README or maintained as a separate document. The key requirement is that it is clearly visible and easy for contributors to find.
- **Discoverability:** An InnerSource project cannot attract contributors if people cannot find it. Projects should therefore be published on a platform that is familiar and accessible to the engineering community, such as an engineering portal, software catalogue, or internal developer platform. Projects should also be clearly identified as InnerSource through agreed metadata, tags, or classifications to improve searchability and visibility.

- ## Blueprint Structure
While implementation details will vary between organisations, a typical InnerSource Blueprint includes the following stages.

**1. Align Stakeholders and Objectives**

Before opening a project to wider collaboration, teams should align on the purpose of InnerSourcing the project and ensure key stakeholders understand the commitment involved.
Key considerations include:
- Why is the project being InnerSourced?
- What outcomes are expected?
- Who are the target users and contributors?

For organisations new to InnerSource, this stage may include engagement with an InnerSource Program Office, platform team, or community of practice to assess readiness and identify gaps.

**2. Establish Project Foundation**

Provide teams with the assets, standards, and guidance needed to create an InnerSource-ready project.

Typical activities include:
 - Configuring repository visibility and access controls
- Applying repository standards and policies
- Providing documentation templates (for example, README and CONTRIBUTING guides)
- Establishing project metadata and InnerSource classifications
- Defining minimum requirements and readiness criteria
- Providing implementation guidance and checklists

The goal is to make it straightforward for teams to set up projects consistently while meeting organisational expectations.

**3. Define Ownership and Governance**

Successful InnerSource projects have clear ownership and decision-making structures.
The blueprint should guide teams to define the ownership model - see ISC patterns. The chosen ownership model will often influence the project's contribution workflow and governance approach.

**4. Establish the Contribution Operating Model**

Contributors should understand how changes move from proposal to implementation.

The blueprint should encourage teams to define:
- How contributions are submitted
- Review and approval expectations
- Review service level objectives (SLOs)
- How contribution decisions are communicated

A predictable contribution experience helps build trust and encourages participation.

**5. Create Communication Channels**

InnerSource is as much about community as it is about code. Projects should establish clear communication channels and document them prominently. Examples include:
- Issues and discussion forums
- Chat or collaboration platforms
- Community meetings

Contributors should be able to easily determine where to ask questions, provide feedback, and engage with core team.

**6. Make the Project Discoverable**

A project cannot attract contributors if it cannot be found. The blueprint should include guidance on publishing projects to locations that are visible and familiar to the engineering community, such as:
- Engineering portals
- Internal developer platforms
- Software catalogues

Projects should also be clearly identified as InnerSource through agreed tags, labels, metadata, or classifications so that engineers can easily discover them.

**7. Validate Readiness and Launch**

The final stage is to formally recognise the project as InnerSource-ready and introduce it to the wider organisation.

Typical launch activities may include:
- Verifying that minimum requirements have been met
- Confirming documentation and governance are in place
- Announcing the project through engineering communication channels

A formal launch creates visibility, signals organisational support, and helps establish momentum for community participation.
